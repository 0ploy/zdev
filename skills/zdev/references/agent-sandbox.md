# Agent sandbox (`zdev claude`, `zdev pi`)

`zdev claude` (the shortcut for `zdev agent run claude`) runs Claude Code in a container of the project, built from a service's image (default `app`); `zdev pi` (`zdev agent run pi`) runs pi in the same sandbox. Inside, `ZDEV_SANDBOX` is set. The session's system prompt describes the specifics; these are the rules that matter.

## When you run in a sandbox

- **zdev commands go to the host and are checked there.** Allowed for this project: `zdev exec`, `logs`, `status`, `info`, `start`, `stop`, `restart`, `update` (`--build`, `--refresh-secrets`). Everything else (`down`, `link`, `cleanup`, `rename`, `--config` to another project) is refused with `zdev: refused (<code>)` and exit 126. Relay the refusal to the developer; don't retry variations.
- **Edit `.zdev/` and apply it with `zdev update`** (`restart` keeps old containers). Applying is refused (`refused (policy)`, with the list) when the config reaches outside the project beyond what the developer applied before: binds outside the project or writable ones of `.git/hooks`/`.git/config`, other 1Password Environments, `traefik.*` labels, `routing.host_port`, hostnames outside the zdev domain or of other projects. Then ask the developer to review `.zdev/` and run `zdev update`. Never change `name:` (`refused (project-changed)`).
- **When your own service changes** (your `zdev update` or the developer's), zdev replaces your container with its new version when your turn ends and resumes the conversation. Until then use `zdev exec app` for what needs the new one; to get the new version here, finish your turn.
- **The app runs in its own container.** `ps` shows only your processes. Use `zdev exec app ps aux`, `zdev logs app`, `zdev restart app`, `zdev exec app <cmd>` for anything that must happen in the running app (supervised processes: `zdev exec app zpctl status`). A `zdev exec` that is interrupted or times out is stopped inside the app container too.
- **Build and test in the sandbox itself:** it has the service's toolchain. Don't start a second instance of the app: you share its data volumes.
- **`zdev run` runs here.** Jobs without `service` run in the sandbox, never on the developer's machine; jobs with `service = "x"` go to that container through the host. Jobs that need host tools (`open`, `op`, ssh keys) fail here.
- **Git only here, never through `zdev exec`.** `.git/hooks` and `.git/config` are read-only: commit and branch, but ask the developer for pushes, remotes and git config.
- **No tool installs:** no root privileges. Add missing tools to the service's Dockerfile and ask the developer to rebuild. `jq`, `gh`, `glab`, `fd` and `rg` are always there (zdev adds static copies at `/opt/zdev/tools`, last on PATH).
- **Network:** the project's services (by name or the project URL) directly; the internet only through the proxy in `HTTPS_PROXY` (logged; HTTPS, no raw TCP/SSH: git over HTTPS). A proxy refusal is a 403 with `X-Zdev-Refused` (curl: "CONNECT tunnel failed, response 403"): relay it, don't debug the network. Under `egress: enforce` only the project's `allow_hosts` work.
- **Git and tokens:** HTTPS only; SSH is off (port 22 refused) and `git@`/`ssh://` remotes of GitHub, GitLab, Bitbucket are rewritten to HTTPS. Granted tokens (`GH_TOKEN` and the like) are placeholders the proxy replaces for their hosts, also when shaped like a real token (`sk-ant-oat01-zdev-placeholder-…`): use git, `gh` and `glab` normally (`GITLAB_TOKEN` for GitLab, also self-hosted), never hunt for the real token. No token: ask the developer to run `zdev agent setup` on the host (GitHub or GitLab), or `zdev agent credentials add <name>` for any other service (npm, Sentry, ...), which only works for tools that send the token in a request header.

## Bootstrap (repository without `.zdev/`)

The sandbox runs zdev's small bootstrap image; zdev commands are refused. Write `.zdev/config.yaml` (see `configuration.md`, `existing-project.md`), then ask the developer to run `zdev start` and `zdev claude --continue`.

## Helping a developer set it up

- Needs `bash` + `git` in the service's image. Missing: `zdev claude` prints the exact Dockerfile lines for the image's package manager (in the service's `dockerfile:`, or a new `.zdev/<service>.Dockerfile` `FROM` its `image:`), and `zdev agent setup` offers to apply them; then `zdev update`.
- Set `services.<name>.mutagen.user` to the app's user, or the agent runs as root (without capabilities).
- Commands, all on the host: `zdev agent setup [claude|pi]` (login check; asks which service's image sessions use when no `app` service decides and several mount the project, stored as `agent.projects.<name>.service`; a GitHub/GitLab token for the project), `zdev agent credentials` (list/add/grant/revoke/test/remove other tokens; `add --preset npm|anthropic`, `--placeholder-prefix` for tools that check a token's shape), `zdev agent update [claude|pi]` (newest Claude Code / build the newest pi now), `zdev claude [service] [args]` and `zdev pi [service] [args]` (a session; every argument goes to the agent, `--help` included).
- Settings live only in `~/.zdev/global-config.yaml` under `agent:`, never in the project config: for every agent `defaults` / `projects.<name>` (`service`, `host_access`, `limits`, `egress`, `allow_hosts`, `credentials`, `docker_socket: accept`) and `host_hook`; Claude-only under `agent.claude` (`channel`, `disable_plugins`) and `agent.projects.<name>.claude.connectors`.
- Terminal integration (e.g. cmux tab icon): `agent.host_hook`, a host command run at session start/end with `ZDEV_AGENT_EVENT` (`SessionStart`/`SessionEnd`), `ZDEV_AGENT` (`claude`/`pi`), `ZDEV_AGENT_PID` (the `zdev claude` PID, outlives sandbox replacements) and Claude-hook JSON on stdin. cmux: `CMUX_CLAUDE_PID=$ZDEV_AGENT_PID cmux claude-hook session-start|session-end`. Recipe in docs/configuration.md.
- A service that mounts the Docker socket makes `zdev claude` refuse the project unless `agent.projects.<name>.docker_socket: accept`.
- Git sync conflict reported by `zdev status`: `zdev mutagen repair-git`.
- Sandbox memory and conversations are separate from Claude on the host (`~/.zdev/agent/claude/projects/<host-path-key>/`, seeded once from the host's memory): `zdev claude --continue` only resumes sandbox conversations.
- Sessions never wait for an agent download/build: a new release comes in the background for the next session (`zdev agent update` now). With none for the image, the session starts it in the background and is refused with a hint; `zdev agent setup [claude|pi]` gets it and waits.
- pi: zdev builds it itself (glibc and musl, same version) from pi's newest release, a few minutes (log: `~/.zdev/agent/pi/build.log`); nothing but the two builds stays. Login: `/login` in a sandbox, shared via `~/.zdev/agent/pi/auth/` (paste the redirect URL: the browser callback can't reach the container). `~/.pi/agent` skills/prompts/themes/extensions and `~/.agents/skills` come along read-only; sessions in `~/.zdev/agent/pi/projects/`. Under `egress: enforce` only Anthropic is pi's own; other providers need `allow_hosts`.
