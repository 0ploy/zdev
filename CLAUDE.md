# zdev

Local development environment framework for web applications. Go CLI that shells out to the `docker` CLI (never the Docker SDK - keeps the door open for Podman). Single command startup, shared infrastructure (Traefik, Mailpit, Adminer), project isolation via Docker networks.

**About this file:** agent guidance only - decisions, conventions, and gotchas that can't be inferred from code. Every line biases behavior and competes for attention. When editing, ask per line: "Would removing this cause an agent to make a mistake?" If not, cut it. Don't add file listings, stack summaries, or anything agents discover by grepping.

## Workflow

- Run `make test` before every commit (fast, mock runtime).
- Run `make test-integration` before releases, or after changing project lifecycle / routing / Mutagen / runtime code (spins up real Docker, takes minutes).
- **Never commit, push, or tag without explicit user confirmation.** Show the proposed commit message and wait for approval before `git commit`, `git push`, or `git tag`. Never add "Co-Authored-By" lines.

Release process:
1. Add a `## vX.Y.Z` section at the top of `CHANGELOG.md` covering the user-visible changes since the last tag (`git log <last-tag>..HEAD` for the candidates).
2. `git add CHANGELOG.md && git commit -m "Release vX.Y.Z"`
3. `git tag vX.Y.Z && git push origin main && git push origin vX.Y.Z`
4. CI builds darwin/linux (arm64/amd64) binaries and creates the GitHub Release from the changelog.

**CHANGELOG entries are for user-visible changes only**: new features, changed behavior, bug fixes a user could hit. Refactors, dead-code cleanup, test/docs/CI work get NO entry - the changelog is a curated story for users, not a commit log. Decide per change; most commits won't warrant an entry.

**Never use em dashes.** Use regular hyphens (-) everywhere: code, copy, comments, docs.

## Conventions That Break Expectations

- **No top-level `volumes:` in project config.** Unlike Docker Compose, named volumes don't need separate declaration - anything in a service `volumes:` entry that doesn't start with `/` or `.` is auto-discovered as a named volume (`parseVolumeMount()`).
- **Config `variables:` are NOT env vars.** They're `${VAR}` placeholders substituted at config-load time (second pass of `LoadProject()`, after `PROJECTNAME` resolves). They don't reach containers - that's what `environment:` is for.
- **`.zdev/local/config.yaml` deep-merges into `.zdev/config.yaml`** before variable substitution (`mergeProjectYAML` in `loader.go`). Maps recurse, scalars and **slices replace** - editing `volumes:` or `mutagen.ignore:` in local means copying the whole list. Don't add a parallel "load local config" path elsewhere; everything flows through `LoadProject` so all consumers see the merged result.
- **Justfile commands** live in `.zdev/commands/<name>.just`, not a single Justfile. Resolution order: built-in > justfile > error. Recipes run with cwd set to the **project root**, not `.zdev/commands/` - so relative paths like `services/app/Dockerfile` in a recipe resolve from the project root the user authored them against.
- **Mutagen auto-detection:** enabled on macOS, disabled on Linux. Controlled by `~/.zdev/global-config.yaml`, not project config.
- **Framework progress messages use `ui.StatusStep()`**, not `fmt.Println` - two blank lines + cyan `▶` + bold text, so they stand out from verbose nested command output. Mirrored by the `zdev step <message>` subcommand for template justfiles (templates should call `@zdev step "..."` instead of `@echo "..."` for top-level progress markers).

## Architecture Anchors

- **`internal/config/defaults.go`** is the single source of truth for images, versions, and the default domain. Change once, everything picks it up.
- **`buildContainerConfig()` in `internal/project/project.go`** is the single source of truth for container configuration. It stamps an `zdev.config-hash` label covering image, env, volumes, command, working dir, routing labels, ports, and network aliases. `zdev update` recreates any service whose stamped hash differs. **Any new service config field that should shape a container must flow through `buildContainerConfig` - otherwise `zdev update` won't detect changes to it.**
- **`services.<name>.dockerfile` builds (`internal/project/build.go`) sit outside the config-hash mechanism**: the built tag stays constant across rebuilds, so the config hash can't see Dockerfile edits. Staleness is a separate `zdev.build-hash` image label - sha256 of Dockerfile contents only, deliberately NOT the build context (source is bind-mounted live). The build context is always the project root. Keep the surface minimal: no args/target/context config - that's the custom-command + `image:` escape hatch; don't grow it toward compose build parity.
- **`runtime.ComputeConfigHash` / `runtime.StampConfigHash` in `internal/runtime/confighash.go`** are the shared hash helpers. Project `buildContainerConfig` and every shared-service `*ContainerConfig` function (`internal/services/adminer.go`, `mail.go`, `redis_insights.go`, `router.go`, `logs.go`, `dns.go`) stamp the same `zdev.config-hash` label. `services.Manager.startService` compares the running container's hash to the freshly built expected config on every call and recreates on mismatch - this is what makes `zdev services start` pick up SSL/image/domain changes instead of silently starting a stale container. **Any new shared-service config field that should shape the container must flow through the `*ContainerConfig` function so it ends up in the hash; don't add per-field comparators.** The router has a port-superset carve-out: `StartRouter` hashes against the UNION of the running container's ports and state-required ports, so extra ports from a now-removed project don't force a recreate. Intentional port shrinking still happens via `RefreshRouter` on project removal.
- **1Password secret resolution (`internal/secrets/`) happens ONLY between hash stamping and `CreateContainer`** in `startServiceWithMutagen`: the config hash covers the UNRESOLVED references plus the attached Environment ID (`zdev.op-env` label), so `serviceNeedsRecreate` stays offline and secret rotation never triggers recreates. Rotation is a separate staleness signal (like build staleness): creation stamps a `zdev.secrets-hash` label (excluded from the config hash), and `zdev update --refresh-secrets` resolves fresh and recreates on mismatch - this also catches variables added/removed in an attached Environment. The resolver fetches whole Environments (`op environment read`, one call per distinct ID, cached per process) - don't add per-key fetching or a second cache layer. On the Update recreate path, `prefetchSecrets` resolves BEFORE the old container is removed so failures keep it intact. Never resolve secrets on the compare path, and never log resolved values or fold op's stdout into errors (stderr only - stdout contains secrets).
- **The local DNS fallback (`zdev dns`, `internal/services/dns.go` + `internal/resolver/`) IS a shared service** - it sits in `AllSharedServices()` and starts FIRST, because on a host whose router enforces DNS rebinding protection it is the only thing making `*.<domain>` resolve: as load-bearing as the router. It doesn't fit the registry's default shape, which is what the three predicates on `SharedServiceDef` are for - **check them instead of assuming**: `HasWebUI()` is false (empty `Subdomain`, no Traefik route - the host talks to its published loopback ports directly), `JoinsProjectNetworks()` is false (`Connect`/`Disconnect` are nil - never dereference them unguarded), and `IsEnabled(mgr)` is the host-level gate that keeps it out of `services start`/`status`/`recreate` on hosts that don't need it. `Enabled` is derived from `resolver.IsInstalled(domain)` (presence of the host split-DNS file), never a config/state flag, so it can't drift from what the OS actually resolves; `ProjectEnabled` is unconditionally true since every project needs name resolution. `services stop` goes through `stopSharedService` in `cmd/services.go` instead of the raw closure: a gated-off service is skipped unless its container is actually running, so a leftover from a since-disabled service still stops without printing "not running" noise on every other machine; `zdev dns disable` is the real off-switch because it reverts the host resolver first. `cmd/dns.go`'s `ensureDNSFallbackRunning` stays despite the registry: `zdev start` and systemcheck verify resolution BEFORE project start would reach the registry. The container is authoritative for `*.<domain>` via a generated `dnsmasq.conf` bind-mounted at `/etc/dnsmasq.conf` (the `dockurr/dnsmasq` entrypoint reads only that path - passthrough CLI flags are ignored); domain changes recreate it via a hashed `zdev.dns-domain` label since the mount's host path is constant. `DNSResolverPort` is **5335, not 5353** (macOS mDNSResponder owns 5353). `runtime.ContainerConfig.RestartPolicy` exists solely for this container's `unless-stopped` and is intentionally absent from `ComputeConfigHash`'s explicit payload (so it doesn't perturb other services' hashes).
- **`ContainerNameFor(service, project)`** builds container names without a loaded `Project`. Use it instead of `fmt.Sprintf("%s.%s.zdev", ...)`.
- **Never hardcode `/var/run/docker.sock` as a bind-mount source.** Use `runtime.HostDockerSocketPath()` (resolves the active context's real socket via `DOCKER_HOST` / `docker context inspect`, falls back to `/var/run/docker.sock`). The legacy host symlink doesn't exist on OrbStack-without-admin or Colima. The in-container target stays `runtime.DefaultDockerSocket`. zdev is engine-agnostic (Docker Desktop / OrbStack / Colima) precisely because it only ever shells out to the `docker` CLI + active context - keep it that way. See `ALTERNATIVE_BACKENDS.md`.
  - **The mount source is not always the CLI endpoint.** On Docker Desktop the active context points at a per-user *proxy* socket (`~/.docker/run/docker.sock`) that the VM's file sharing can't bind-mount (`mkdir ... operation not supported`); only the special-cased `/var/run/docker.sock` works. So `HostDockerSocketPath()` redirects to `/var/run/docker.sock` when the endpoint is a Docker Desktop proxy socket and that socket exists (detected by the `/.docker/` path segment - OrbStack/Colima paths don't match and pass through unchanged). When it doesn't exist (the "Allow the default Docker socket" setting is off), there is nothing mountable: **call `runtime.CheckDockerSocketMountable()` before starting any socket-mounting container** (`StartRouter`, `StartLogs`, and `checkDocker` in systemcheck already do) so the user gets the actionable "enable the default socket" message instead of the raw daemon error. `runtime.ContainerConfig` mounts the socket for the router and Dozzle only.
- **Link networks** are runtime relationships between projects, stored in global state (`~/.zdev/state.yaml`), not project config. Each creates a `zdev_link_<name>` network. Containers resolve each other by container name via Docker's embedded DNS.
- **Template repos** follow the naming convention `zdev-template-<name>` (matters for `zdev create` resolution).
- **Create-time scaffold hook (`internal/project/scaffold.go`, wired in `cmd/create.go`).** If a template ships `.zdev/scaffold.sh`, `zdev create` runs it once in a throwaway `docker run --rm --entrypoint sh` with the project bind-mounted at `/app` (via `runtime.RunContainer` / `RunConfig`) - the `--entrypoint sh` override bypasses the image's own init (zpinit, PHP entrypoint), so the mechanism is process-manager agnostic, not zpinit-coupled. It builds/pulls the scaffold service's image first (sole service, or the one named `app`), reusing the same `zdev-<project>-<service>` tag `zdev start` will use. On success the hook is renamed to `scaffold.sh.disabled` (never deleted); `ScaffoldHookPath` ignores `.disabled`. This keeps scaffolding out of the created project - no `.setup-complete` gate, no re-scaffolding `setup.just`. Install belongs in the boot path, not the hook.

## Adding Docker-Dependent Commands

Use `withProject(timeout, fn)` or `withDocker(timeout, fn)` from `cmd/shared.go`. They handle the context, `requireDocker` check, and (for `withProject`) `project.Load` in one line. Without the Docker check users get cryptic low-level failures instead of a clear "Docker isn't running" message.

### Adding a Shared Service

Easy-to-miss steps when wiring a new shared service:

1. Container name constant in `internal/services/<service>.go`.
2. `<Service>ContainerConfig(...)` built on `webUIContainerConfig` (`internal/services/webui.go`) - it owns the Traefik label wiring and stamps the config hash; only port/alias/env/volumes vary per service (see `mail.go` for the minimal case, `logs.go` for one with extras).
3. `Start<Service>` and `<Service>Status` on `manager.go`. No per-service Stop/Connect/Disconnect methods - those come from the registry closures.
4. Add an entry to `AllSharedServices()` in `internal/services/registry.go` using `stopClosure` / `connectClosure` / `disconnectClosure` - **`connectClosure` must get the network alias** so project containers can resolve the service by short name. This single registry drives CLI start/stop/status, `services recreate`, and per-project connect/disconnect. **Do not add parallel registries in `cmd/` or `internal/project/`.** Leave `Subdomain` empty only if the service has no web UI, `Connect`/`Disconnect` nil only if it never joins project networks, and `Enabled` nil unless it exists on some hosts and not others - consumers branch on `HasWebUI()` / `JoinsProjectNetworks()` / `IsEnabled(mgr)`, so a new combination means auditing them.
5. Add the image constant to `internal/config/defaults.go`.
6. Add the per-project opt-in flag to `ProjectSharedConfig` in `internal/config/config.go` and reference it in the registry's `ProjectEnabled` closure.

## Gotchas

- **Project domains don't work for inter-container communication.** `*.0ploy.dev` resolves to 127.0.0.1, which inside a container points at the container itself, not Traefik. Cross-project containers must use container names (`app.project-b.zdev`) - this is why `zdev link` uses Docker DNS, not routing.
- **Mutagen ignored paths are not synced either way.** `node_modules` and `.pnpm-store` must be ignored for Node.js projects so they stay inside the container at native speed. IDE autocomplete still works via the host's own `pnpm install` / host `node_modules`.
- **`.pnpm-store` MUST be in the mutagen ignore list for pnpm projects.** pnpm builds a ~500MB content-addressable store with platform-specific native binaries (glibc vs musl) inside the project dir. Without ignoring it, syncing those binaries to the host breaks the next time the container image changes.
- **Only directory bind mounts sync via Mutagen.** Single-file mounts stay as regular bind mounts.
- **Sync-ready gate:** `buildContainerConfig` wraps commands with a wait on `/.zdev-sync-ready` when Mutagen is enabled for that service. Don't add your own `while [ ! -f ... ]` workaround - it's already there.
- **Every container-creation path must run `prepareMutagen()` first and pass the resulting `mountMap` into `startServiceWithMutagen` / `buildContainerConfig`.** Building a container with `mutagenEnabled=false` while the project actually has Mutagen mounts swaps the named `sync.<svc>.<project>.zdev` volume for a raw bind mount - dropping anything in the Mutagen ignore list (`vendor/`, `.setup-complete`) that lived only inside the volume. Has burned `zdev update` twice; covered by `TestProject_MutagenUpdatePreservesSyncVolume`.
- **Per-service Mutagen ownership (`services.<name>.mutagen.user/group/file_mode/directory_mode`)** maps to Mutagen's `--default-*-beta` flags and addresses the "files synced as root, but apache runs as www-data and can't read them" class of bugs. Drift is tracked via a hash file at `~/.zdev/mutagen/sessions/<session-name>`; on change `startMutagenSessions` terminates+recreates the session, and `applyPostSyncOwnership` runs `chown -R` inside the container so PRE-EXISTING files also pick up the new owner (Mutagen's flags only stamp NEW files). Don't drop the chown step thinking the flags handle it - they don't.
- **`zdev rename` migrates volumes via a temp container** using a project service image (guaranteed present locally). Docker has no native volume rename. See `CopyVolume` on the Runtime interface. All copies happen before any old volumes are removed, to bound blast radius on failure.
- **The docs page (`docs.shared.<domain>`) is also Traefik's 404 catch-all** - unmatched URLs land there, not a generic error page.
- **Integration tests that tear down shared services** (router, mail, db, redis, logs) must snapshot beforehand and restore afterward via `snapshotSharedServices` / `restoreSharedServices`. Forgetting this silently breaks the developer's running environment.
- **New config fields break released binaries.** Config parsing uses `KnownFields(true)`, so a `.zdev/config.yaml` using an unreleased field fails to load on every installed zdev. Never adopt an unreleased config feature in a real project's config - it bricks the team's environment until the release ships.
