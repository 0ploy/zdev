# zdev

Local development environment framework for web applications. Go CLI that shells out to the `docker` CLI (never the Docker SDK - keeps the door open for Podman). Single command startup, shared infrastructure (Traefik, Mailpit, Adminer), project isolation via Docker networks.

**About this file:** agent guidance only - decisions, conventions, and gotchas that can't be inferred from code. Every line biases behavior and competes for attention. When editing, ask per line: "Would removing this cause an agent to make a mistake?" If not, cut it. Don't add file listings, stack summaries, or anything agents discover by grepping.

## Workflow

- **The Go toolchain lives in the `app` container (`.zdev/`), not on the host.** On the host use `zdev run test unit` / `zdev run test vet` / `zdev run build` / `zdev run install`; in a `zdev claude` sandbox `go` and `make` work directly.
- Run `zdev run test all` (vet + unit, mock runtime) before every commit.
- Run `zdev run test integration` before releases, or after changing project lifecycle / routing / Mutagen / runtime code (real Docker, takes minutes). It compiles test binaries for the host in the container and runs them on the host, so it is refused in a sandbox: ask the developer to run it.
- **Never commit, push, or tag without explicit user confirmation.** Show the proposed commit message and wait for approval before `git commit`, `git push`, or `git tag`. Never add "Co-Authored-By" lines.

Release process:
1. Add a `## vX.Y.Z` section at the top of `CHANGELOG.md` covering the user-visible changes since the last tag (`git log <last-tag>..HEAD` for the candidates).
2. `git add CHANGELOG.md && git commit -m "Release vX.Y.Z"`
3. `git tag vX.Y.Z && git push origin main && git push origin vX.Y.Z`
4. The tag runs `.github/workflows/release.yml`: it extracts the `CHANGELOG.md` section whose heading is exactly the tag (`## vX.Y.Z`) and **fails the release if there is none** (a `## v0.1.1` tag never picks up `## v0.1.10`), runs the tests, builds darwin/linux (arm64/amd64) binaries, checks the linux-amd64 one reports the tag (an `-X` path that matches no variable is silently ignored by the linker and ships a `dev` binary that breaks `self-update`), writes `checksums.txt` (verified by `install.sh` and `self-update`) and creates the GitHub Release.
5. If it fails, nothing is published: fix on `main`, then move the tag (`git tag -f vX.Y.Z && git push -f origin vX.Y.Z`) or cut the next patch.

Actions in the workflows are pinned to commit SHAs with the version in a trailing comment; Renovate bumps both. By hand, get the commit with `gh api repos/<owner>/<repo>/commits/<tag> --jq .sha` (not `git/refs/tags/<tag>`, which returns the tag object for annotated tags).

**Renovate** (`renovate.json`, self-hosted nightly in `.github/workflows/renovate.yml` as a GitHub App of ours) tracks every pin: Go and its modules, `.zdev/Dockerfile`, the actions, and the `defaults.go` pins. It can't compute checksums, so a tool bump runs `go run ./scripts/pinsums -w` (postUpgradeTasks, the only command the workflow allows) and CI checks them with `go run ./scripts/pinsums`.

**CHANGELOG entries are for user-visible changes only**: new features, changed behavior, bug fixes a user could hit. Refactors, dead-code cleanup, test/docs/CI work get NO entry - the changelog is a curated story for users, not a commit log. Decide per change; most commits won't warrant an entry.

## Style

**Never use em dashes.** Use regular hyphens (-) everywhere: code, copy, comments, docs.

## Conventions That Break Expectations

- **No top-level `volumes:` in project config.** Unlike Docker Compose, named volumes don't need separate declaration - anything in a service `volumes:` entry that doesn't start with `/` or `.` is auto-discovered as a named volume (`parseVolumeMount()`).
- **Config `variables:` are NOT env vars.** They're `${VAR}` placeholders substituted at config-load time (second pass of `LoadProject()`, after `PROJECTNAME` resolves). They don't reach containers - that's what `environment:` is for.
- **`.zdev/local/config.yaml` deep-merges into `.zdev/config.yaml`** before variable substitution (`mergeProjectYAML` in `loader.go`). Maps recurse, scalars and **slices replace** - editing `volumes:` or `mutagen.ignore:` in local means copying the whole list. Don't add a parallel "load local config" path elsewhere; everything flows through `LoadProject` so all consumers see the merged result.
- **Project commands are `.zdev/run/<cmd>.toml` job files run via `zdev run`**, never resolved as `zdev <cmd>` (that shorthand is only for deprecated `.zdev/commands/*.just`, built-in > justfile, and goes away with just). Host jobs run with cwd = **project root**. Don't add a `run:`/`commands:` section to `.zdev/config.yaml` (new config keys brick released binaries); job files treat unknown keys as warnings on purpose.
- **`zdev run` never substitutes into script bodies.** Arguments reach scripts as `"$@"`; `{N}`/`{all}` placeholders exist only in non-shell TOML fields (`needs`, `workdir`, `env`, `script`, `confirm`), which are never passed through a shell.
- **The shell prelude shares a line with the job body's first line** so shell error line numbers match the job file. bash 3.x (macOS) and busybox ash report `-c` line numbers one too low and get the body on its own line instead (`preludeSep`, `containerLauncher` in `internal/run/exec.go`). Don't add lines before the body without keeping this.
- **Mutagen auto-detection:** enabled on macOS, disabled on Linux. Controlled by `~/.zdev/global-config.yaml`, not project config.
- **Framework progress messages use `ui.StatusStep()`**, not `fmt.Println` - two blank lines + cyan `▶` + bold text, so they stand out from verbose nested command output. Job scripts mirror it with the `step "..."` helper from the run prelude (templates use `step` instead of `echo` for top-level progress markers); `zdev step` remains only for legacy justfiles.

## Architecture Anchors

- **`internal/config/defaults.go`** is the single source of truth for images, tool releases (`ToolRelease`: mkcert, just, mutagen, the sandbox's tools, Bun), and the default domain. Every pin carries a `// renovate:` comment on the line above it, in one of the shapes `renovate.json`'s regex managers match; tests enforce the shapes, check that the config finds every marker (`TestRenovateConfigMatchesDefaults`), and reject markers anywhere else. A new `ToolRelease` goes into `ToolReleases` too, or its checksums are never refreshed.
- **`buildContainerConfig()` in `internal/project/project.go`** is the single source of truth for container configuration. It stamps an `zdev.config-hash` label covering image, env, volumes, command, working dir, routing labels, ports, and network aliases. `zdev update` recreates any service whose stamped hash differs. **Any new service config field that should shape a container must flow through `buildContainerConfig` - otherwise `zdev update` won't detect changes to it.**
- **`services.<name>.dockerfile` builds (`internal/project/build.go`) sit outside the config-hash mechanism**: the built tag stays constant across rebuilds, so the config hash can't see Dockerfile edits. Staleness is a separate `zdev.build-hash` image label - sha256 of Dockerfile contents only, deliberately NOT the build context (source is bind-mounted live). The build context is always the project root. Keep the surface minimal: no args/target/context config - that's the custom-command + `image:` escape hatch; don't grow it toward compose build parity. A start or update that built prunes the dangling images carrying `zdev.build-hash` (`pruneReplacedBuilds`), the builds the new ones replaced; Docker's build cache is left alone (it is what keeps rebuilds fast, and it can't be scoped to zdev).
- **`runtime.ComputeConfigHash` / `runtime.StampConfigHash` in `internal/runtime/confighash.go`** are the shared hash helpers. Project `buildContainerConfig` and every shared-service `*ContainerConfig` function (`internal/services/adminer.go`, `mail.go`, `redis_insights.go`, `router.go`, `logs.go`, `dns.go`) stamp the same `zdev.config-hash` label. `services.Manager.startService` compares the running container's hash to the freshly built expected config on every call and recreates on mismatch - this is what makes `zdev services start` pick up SSL/image/domain changes instead of silently starting a stale container. **Any new shared-service config field that should shape the container must flow through the `*ContainerConfig` function so it ends up in the hash; don't add per-field comparators.** A recreate onto a new image removes the old one once the new container runs (`removeReplacedImage`; never forced). The router has a port-superset carve-out: `StartRouter` hashes against the UNION of the running container's ports and state-required ports, so extra ports from a now-removed project don't force a recreate. Intentional port shrinking still happens via `RefreshRouter` on project removal.
- **`ComputeConfigHash` hashes `Command` IN ORDER** (unlike Env/Labels/Volumes/Ports/Aliases, which it sorts). Anything that turns a collection into command arguments must therefore feed it a deterministic order. This bit the router: `state.GetAllRoutingPorts` returned ports in Go map iteration order, `StartRouter`'s compare path sorted them via `unionPortSets` but its create path passed them raw, so the created container's hash never matched the expected one - "Router config drift detected, recreating..." on every `zdev start` of any project, forever. `GetAllRoutingPorts` now sorts and `buildRouterContainerConfig` sorts again defensively; keep both.
- **A shared service's project-network attachments exist ONLY in the Docker daemon.** Nothing in project config or `~/.zdev/state.yaml` lists them - they are created one at a time by `connectEnabledSharedServices` as each project starts. So a container recreate silently detaches the service from every project except the one whose lifecycle triggered it, and the symptom (other projects 502) points nowhere near the cause. **Every path that removes a shared container must call `snapshotProjectNetworks` before and `restoreProjectNetworks` after** - after CREATE, before START (a created container accepts network connects, so a failed start keeps the attachments for the next plain start), and pull the image before removing so a failed pull keeps the old container - `startService`, `StartRouter`, `RefreshRouter` (which snapshots itself, since by the time `StartRouter` runs the container is gone, and hands the snapshot to `startRouter`) and `cmd/services.go`'s `recreate` (via the exported `SnapshotProjectNetworks` / `RestoreProjectNetworks`). The snapshot excludes `zdev_shared` (the creation network comes back from the container config) and skips networks that no longer exist on restore.
- **1Password secret resolution (`internal/secrets/`) happens ONLY between hash stamping and `CreateContainer`** in `startServiceWithMutagen`: the config hash covers the UNRESOLVED references plus the attached Environment ID (`zdev.op-env` label), so `serviceNeedsRecreate` stays offline and secret rotation never triggers recreates. Rotation is a separate staleness signal (like build staleness): creation stamps a `zdev.secrets-hash` label (excluded from the config hash), and `zdev update --refresh-secrets` resolves fresh and recreates on mismatch - this also catches variables added/removed in an attached Environment. The resolver fetches whole Environments (`op environment secret list --reveal --format json`, op 2.42+, one call per distinct ID, cached per process) - don't add per-key fetching or a second cache layer. On the Update recreate path, `prefetchSecrets` resolves BEFORE the old container is removed so failures keep it intact. Never resolve secrets on the compare path, and never log resolved values or fold op's stdout into errors (stderr only - stdout contains secrets).
- **The local DNS fallback (`zdev dns`, `internal/services/dns.go` + `internal/resolver/`) IS a shared service** - it sits in `AllSharedServices()` and starts FIRST, because on a host whose router enforces DNS rebinding protection it is the only thing making `*.<domain>` resolve: as load-bearing as the router. It doesn't fit the registry's default shape, which is what the three predicates on `SharedServiceDef` are for - **check them instead of assuming**: `HasWebUI()` is false (empty `Subdomain`, no Traefik route - the host talks to its published loopback ports directly), `JoinsProjectNetworks()` is false (`Connect`/`Disconnect` are nil - never dereference them unguarded), and `IsEnabled(mgr)` is the host-level gate that keeps it out of `services start`/`status`/`recreate` on hosts that don't need it. `Enabled` is derived from `resolver.IsInstalled(domain)` (presence of the host split-DNS file), never a config/state flag, so it can't drift from what the OS actually resolves; `ProjectEnabled` is unconditionally true since every project needs name resolution. `services stop` goes through `stopSharedService` in `cmd/services.go` instead of the raw closure: a gated-off service is skipped unless its container is actually running, so a leftover from a since-disabled service still stops without printing "not running" noise on every other machine; `zdev dns disable` is the real off-switch because it reverts the host resolver first. `cmd/dns.go`'s `ensureDNSFallbackRunning` stays despite the registry: `zdev start` and systemcheck verify resolution BEFORE project start would reach the registry. The container is authoritative for `*.<domain>` via a generated `dnsmasq.conf` bind-mounted at `/etc/dnsmasq.conf` (the `dockurr/dnsmasq` entrypoint reads only that path - passthrough CLI flags are ignored); domain changes recreate it via a hashed `zdev.dns-domain` label since the mount's host path is constant. `DNSResolverPort` is **5335, not 5353** (macOS mDNSResponder owns 5353). `runtime.ContainerConfig.RestartPolicy` exists solely for this container's `unless-stopped` and is intentionally absent from `ComputeConfigHash`'s explicit payload (so it doesn't perturb other services' hashes).
- **Per-project certificates (`internal/ssl/projectcerts.go`, `internal/project/certs.go`) cover routed hosts the main wildcard can't** (nested deeper than one label, or outside the domain). The PROJECT lifecycle owns them (`ensureProjectCert` in `registerAndConnect`, AFTER registration - the router's orphan sweep would delete a cert issued for a not-yet-registered project; removal wherever a project is unregistered) because only project config knows the hostnames; the router side (`refreshProjectCerts` in `StartRouter`) only sweeps orphans and re-signs on a CA change using each cert's existing SANs. Hosts come from `routedHosts()`, built on the same `routesService`/`routingHost` helpers as the labels - never derive them separately. The cert sits outside the config hash (no container recreate). `project-<name>.yaml` embeds the cert's sha256 on purpose: Traefik watches only the dynamic dir, so a cert rewritten under an unchanged yaml is never reloaded. Keys are `<name>.key`, not `<name>-key.pem`, which collides with a project named `<name>-key`.
- **Agent sandboxes (`zdev claude`: `cmd/claude.go`, `cmd/sandbox.go`, `internal/agent/`, `internal/project/agent.go`; design in `PLAN_2_AGENT_SANDBOX.md`).** Claude Code runs in a per-session container built from a service's config through `AgentBaseConfig` (= `buildContainerConfig` + resolved secrets, with the service's name, alias, ports, labels and command stripped, so it never takes the service's traffic or routes). Things that look removable and aren't:
  - **Sandboxes carry `zdev.sandbox.*` labels, never `zdev.project`**: `removeStaleProjectContainers` deletes every `zdev.project` container that isn't a configured service, so the next `zdev start` would kill running sessions.
  - **zdev's own agent commands live under `zdev agent` (`cmd/agent.go`), never as subcommands of `zdev claude`**: `zdev claude` is the shortcut for `zdev agent run claude` and passes every argument to Claude (`--help` included), because Claude has subcommands of its own (`update`, `auth`, `mcp`...) and any shared name would shadow one. Same for `zdev pi`. Agent-only settings go in `agent.<agent>` / `agent.projects.<p>.<agent>`, an agent's state under `~/.zdev/agent/<agent>/`.
  - **What differs per agent sits behind `codingAgent` (`cmd/agent_kinds.go`)**: build, home preparation, command line, resume. Everything else in `runSandbox` is shared; don't branch on the agent there.
  - **A session never waits for an agent download or build** (`codingAgent.install`): newer releases come in the background; with none for the image it starts one in the background and refuses with a hint. Only `zdev agent setup` (`ensure`) and `zdev agent update` wait. Background pi builds are a detached `zdev agent update pi` serialized by a file lock; Claude's are detached `zdev-fill-<volume>` containers, which `EnsureClaude` waits for instead of downloading twice.
  - **Throwaways are removed by whoever creates them, and sweeps catch what a crash left**: one-shot containers run with `--rm`; a pi build's cache volume and (when it pulled it) the Node image go in a `defer` that outlives a cancelled ctx; `MarkUsed` records every `zdev.agent` volume except homes, so failed downloads too reach the superseded/14-day sweep, and moved helper pins are removed (`sweepHelperImages`). A new throwaway needs one of these paths, or it piles up silently.
  - **pi is built on the developer's machine, never downloaded as a binary** (`internal/agent/pi.go`): pi's official Linux builds are glibc-only, so one run builds both libc variants from the release's source archive and they always match. The musl launcher sets `LD_LIBRARY_PATH` (bundled libstdc++) only when the image lacks libstdc++, and zdev's pi extension strips it before pi spawns anything, so the image's own tools never load ours: keep both halves. zdev passes pi no `--session-id` (pi warns about every new one); the extension reports pi's session id with each turn end and a replaced sandbox resumes that.
  - **Every check runs on the host**: the in-container zdev forwards commands over a relay (SSH protocol over the stdio of a `docker exec -i`, host is the server) and the container side is untrusted. Allowlist and refusals live in `agent.CheckRequest` and `relayHandler`; never move a check into the client. `zdev run` runs in the sandbox (host jobs must never reach the developer's machine) with `agent.RelayRuntime` for its container steps.
  - **A cancelled relayed exec is killed by marker**: a killed `docker exec` client leaves its process running in the container, so relayed execs carry `ZDEV_EXEC_MARK` (DockerCLI.Exec passes it on with `-e` when set) and the host kills the processes carrying it (`agent.KillMarkedScript`).
  - **The relay stops the container when its stdin closes**: a killed `docker exec -it` client leaves Claude running inside, so the relay is the lifeline; `SweepOrphans` (by the `zdev.sandbox.pid` label) is the backstop.
  - **`.zdev` and `.git` sync only for the agent's mount**: `sessionIgnores` appends `!.zdev`, `!.git` (a later negation beats the built-in `.git` and a template's `.zdev` ignore), gated by the host-side marker `~/.zdev/agent/sync/<project>`. **`.git/hooks` and `.git/config` are ignored LAST in every session of such a project** (`agentGitGuards`): the Mac runs them without anyone deciding to, and every container mounting the sync volume can write them (the app through `zdev exec`), so a read-only mount in the agent container alone isn't enough. The agent sees the Mac's copies as read-only binds. Native binds (Linux, `no_sync`) are the host directory itself: `buildContainerConfig` adds read-only guard mounts over both paths in every writable host bind containing them (`gitGuardMounts`, in the hash), and `zdev claude` recreates services lacking only those (`ApplyAgentGitGuards`).
  - **Lifecycle commands from a sandbox are checked in the process that applies them**: the relay runs host zdev with `ZDEV_AGENT_REQUEST=<project>`; `LoadFromDir` then refuses a config with another `name:` (it would act on another project's containers), and `agentGate` refuses (exit 126) what `CheckAgentPolicy` finds beyond the baseline. The baseline (`~/.zdev/agent/approved/<project>.json`) is recorded after the developer's own start/update/restart, from the config for up-to-date containers and from the running container for outdated ones. Checking in the relay instead would read the config twice (check, then apply). **`${VAR}` in such a request reads only the host env names the baseline recorded (`EnvNames`)**: the agent writes `.zdev/` and `zdev info` prints the substituted config, so the full env would hand it the developer's tokens. `internal/config` fails closed (no lookup registered, no host env); don't pass a filtered `os.Environ()` to the relay child instead, the child itself needs `OP_*`, `DOCKER_*` and friends. **A new project config field fails `TestAgentPolicyClassifiesFields`** until it is classified; one that reaches outside containers needs a rule first.
  - **The managed `Stop` hook (`zdev sandbox turn-end`) is how a stale sandbox gets replaced**: only at a turn's end, never mid-turn; `claudeSession` loops over `runSandbox` and resumes with `--resume`. It must stay quiet and exit 0 (a hook error shows in Claude).
  - **The egress proxy (`agent.Egress`) runs on the host**, so its address rules are as critical as the fence: every resolved address must be public and the connection goes to the checked address, never the name again (DNS rebinding); project domains are refused there (they resolve to the host's 127.0.0.1) and reached via `NO_PROXY`. The fence's `ProxyOnly` is what makes the proxy the only way out.
  - **Tokens never enter the sandbox**: it holds placeholders; the proxy intercepts TLS only for credential hosts (session CA, in memory) and swaps them in. Don't log header values, and don't add SSH (port 22 is refused on purpose: HTTPS only, see the decision log in PLAN_2).
  - **The relay flushes the agent's sync session before commands that read `.zdev/` on the host**: the agent edits it in its container, the host reads the Mac's copy.
  - **In the sandbox the project must resolve under the host's names**: templates use `name: ${PROJECTDIR}` and the source sits at `/app`, so `buildVariables` takes `ZDEV_HOST_PROJECTDIR` when `ZDEV_SANDBOX` is set.
  - The `runtime.ContainerConfig` fields after `RestartPolicy` (user, caps, limits, `Mounts`) are for the sandbox only and stay out of `ComputeConfigHash`. `Entrypoint` is hashed only when set (the sync gate's wrapper), so other containers' hashes don't change.
  - Dev builds have no release to download the Linux zdev from: put `zdev-linux-<arch>` next to the binary or set `ZDEV_AGENT_LINUX_BINARY`.
- **`ContainerNameFor(service, project)`** builds container names without a loaded `Project`. Use it instead of `fmt.Sprintf("%s.%s.zdev", ...)`.
- **Never hardcode `/var/run/docker.sock` as a bind-mount source.** Use `runtime.HostDockerSocketPath()` (resolves the active context's real socket via `DOCKER_HOST` / `docker context inspect`, falls back to `/var/run/docker.sock`). The legacy host symlink doesn't exist on OrbStack-without-admin or Colima. The in-container target stays `runtime.DefaultDockerSocket`. zdev is engine-agnostic (Docker Desktop / OrbStack / Colima) precisely because it only ever shells out to the `docker` CLI + active context - keep it that way. See `ALTERNATIVE_BACKENDS.md`.
  - **The mount source is not always the CLI endpoint.** On Docker Desktop the active context points at a per-user *proxy* socket (`~/.docker/run/docker.sock`) that the VM's file sharing can't bind-mount (`mkdir ... operation not supported`); only the special-cased `/var/run/docker.sock` works. So `HostDockerSocketPath()` redirects to `/var/run/docker.sock` when the endpoint is a Docker Desktop proxy socket and that socket exists (detected by the `/.docker/` path segment - OrbStack/Colima paths don't match and pass through unchanged). When it doesn't exist (the "Allow the default Docker socket" setting is off), there is nothing mountable: **call `runtime.CheckDockerSocketMountable()` before starting any socket-mounting container** (`StartRouter`, `StartLogs`, and `checkDocker` in systemcheck already do) so the user gets the actionable "enable the default socket" message instead of the raw daemon error. `runtime.ContainerConfig` mounts the socket for the router and Dozzle only.
- **Link networks** are runtime relationships between projects, stored in global state (`~/.zdev/state.yaml`), not project config. Each creates a `zdev_link_<name>` network. Containers resolve each other by container name via Docker's embedded DNS.
- **Template repos** follow the naming convention `zdev-template-<name>` (matters for `zdev create` resolution).
- **Create-time scaffold hook (`internal/project/scaffold.go`, wired in `cmd/create.go`).** If a template ships `.zdev/scaffold.sh`, `zdev create` runs it once in a throwaway `docker run --rm --entrypoint sh` with the project bind-mounted at `/app` (via `runtime.RunContainer` / `RunConfig`) - the `--entrypoint sh` override bypasses the image's own init (zpinit, PHP entrypoint), so the mechanism is process-manager agnostic, not zpinit-coupled. It builds/pulls the scaffold service's image first (sole service, or the one named `app`), reusing the same `zdev-<project>-<service>` tag `zdev start` will use. On success the hook is renamed to `scaffold.sh.disabled` (never deleted); `ScaffoldHookPath` ignores `.disabled`. This keeps scaffolding out of the created project - no `.setup-complete` gate, no re-scaffolding setup command. Install belongs in the boot path, not the hook.

## Adding Docker-Dependent Commands

Use `withProject(timeout, fn)` or `withDocker(timeout, fn)` from `cmd/shared.go`. They handle the context, `requireDocker` check, and (for `withProject`) `project.Load` in one line. Without the Docker check users get cryptic low-level failures instead of a clear "Docker isn't running" message.

### Adding a Shared Service

Easy-to-miss steps when wiring a new shared service:

1. Container name constant in `internal/services/<service>.go`.
2. `<Service>ContainerConfig(...)` built on `webUIContainerConfig` (`internal/services/webui.go`) - it owns the Traefik label wiring and stamps the config hash; only port/alias/env/volumes vary per service (see `mail.go` for the minimal case, `logs.go` for one with extras).
3. `Start<Service>` and `<Service>Status` on `manager.go`. No per-service Stop/Connect/Disconnect methods - those come from the registry closures.
4. Add an entry to `AllSharedServices()` in `internal/services/registry.go` using `stopClosure` / `connectClosure` / `disconnectClosure` - **`connectClosure` must get the network alias** so project containers can resolve the service by short name. This single registry drives CLI start/stop/status, `services recreate`, and per-project connect/disconnect. **Do not add parallel registries in `cmd/` or `internal/project/`.** Leave `Subdomain` empty only if the service has no web UI, `Connect`/`Disconnect` nil only if it never joins project networks, and `Enabled` nil unless it exists on some hosts and not others - consumers branch on `HasWebUI()` / `JoinsProjectNetworks()` / `IsEnabled(mgr)`, so a new combination means auditing them.
5. Add the image constant to `internal/config/defaults.go`.
6. Add the per-project opt-in flag to `ProjectSharedConfig` in `internal/config/config.go` and reference it in the registry's `ProjectEnabled` closure.

## Gotchas

- **Project domains work inside containers only through router aliases.** `*.0ploy.dev` resolves publicly to 127.0.0.1, the container itself. `ConnectRouter` (`internal/services/router_aliases.go`) joins the router to each project network with every registered project's `resolvableHosts()` (stored as `Hosts` in state) plus the shared UI hosts as aliases, which Docker DNS answers before the public record. Docker can't edit an endpoint's aliases, so a changed set means disconnect + reconnect: only reconnect when the set differs (`sameStringSet`), never on every start - it drops in-flight requests to that project. `restoreProjectNetworks` swaps in fresh router aliases instead of the snapshot's. Projects whose state entry lacks `hosts_recorded` (registered by an older zdev or `RegisterProject`) get their hosts backfilled from their config on disk by `backfillRoutedHosts` at every start/update, so an upgrade needs no restarts. `zdev start`/`restart` reuse existing containers but print a `zdev update` hint when the config hash drifted (`warnOutdatedServices`). No wildcards: only config hostnames, and only those under the zdev domain (`routerAliases` filters - an outside alias would hijack that domain for every project's containers, which trust the zdev CA). Alias sets are compared via `managedAliases` (Docker <25 adds the short container ID), and `ConnectRouter` runs under `state.WithRouterLock` so concurrent starts can't restore an older set. Containers trust the zdev CA via `applyCATrust` (`internal/project/certs.go`): `~/.zdev/trust` (never `~/.zdev/certs`, which holds private keys) mounted read-only at `/etc/zdev`, plus `ca-bundle.pem` (host public roots + mkcert root, built by `SyncCATrust`) mounted over the three system CA paths, plus `NODE_EXTRA_CA_CERTS`/`REQUESTS_CA_BUNDLE`. The bundle must stay a complete trust store (no host roots = no bundle), and `SyncCATrust` must write IN PLACE: single-file mounts pin the inode, so a rename-replace leaves running containers on the old file.
- **Mutagen ignored paths are not synced either way.** `node_modules` and `.pnpm-store` must be ignored for Node.js projects so they stay inside the container at native speed. IDE autocomplete still works via the host's own `pnpm install` / host `node_modules`.
- **`.pnpm-store` MUST be in the mutagen ignore list for pnpm projects.** pnpm builds a ~500MB content-addressable store with platform-specific native binaries (glibc vs musl) inside the project dir. Without ignoring it, syncing those binaries to the host breaks the next time the container image changes.
- **Only directory bind mounts sync via Mutagen.** Single-file mounts stay as regular bind mounts.
- **`services.<name>.mutagen.no_sync` is the escape hatch from sync, and it is a correctness feature, not a tuning knob.** Containers are created and started BEFORE `finalizeMutagen` resumes and flushes the sessions, so a sync volume is empty while the entrypoint runs. Any directory read once during startup (`/docker-entrypoint-initdb.d`, nginx `conf.d`, certs) must be listed there to stay a native bind. Entries are validated against the service's own mount paths - a typo would silently sync the directory and the symptom (a database that comes up empty) points nowhere near the cause.
- **Create sessions only through `createSyncSession`** (`mutagen_sync.go`), never `m.CreateSession` directly: a new two-way-safe session has no common ancestor, so against a volume holding a previous session's files every difference is a conflict it never resolves and the gate holds forever. `createSyncSession` runs a two-way-resolved pass first (host wins), then the configured mode.
- **Sync identity is per MOUNT, not per service (`SyncNames` in `mutagen_sync.go`).** A service with one directory bind keeps the historic `sync.<svc>.<project>.zdev` / `zdev-<project>-<svc>` names; with two or more, every mount is named after its container path. Sharing a name across a service's mounts is what made the second bind lose both its session (the existence check found its sibling and skipped it - `SessionConfig.Hash()` deliberately excludes Alpha/Beta, so the hash matched too) and its volume (the lookup map kept only the last mount). `zdev rename` has to reproduce the rule for the new project name, so it goes through `SyncNames` as well - don't inline the naming anywhere else.
- **Sync-ready gate:** `buildContainerConfig` wraps commands with `SyncGateCommand`, a wait on `/tmp/.zdev-sync-ready`, when Mutagen is enabled for that service. A synced service WITHOUT `command:` gets its image's ENTRYPOINT+CMD wrapped instead (`imagegate.go`: `--entrypoint sh -c <gate>; exec "$@"`). Those image facts come from `resolveImageGate`, which every path calls before `buildContainerConfig` for such a service (create, the update compare, `AgentBaseConfig`, `ApplyAgentGitGuards`) - a new path that skips it builds an unwrapped config whose hash differs, so the service shows as outdated forever. `ImageEntrypoint` reads them from a created-not-started container, because inspecting a multi-platform image by tag can return an empty Config with the containerd image store. **The marker lives in /tmp on purpose**: the wrapper runs as the image's default user, and on percona, postgres and friends that user cannot write to `/` - it could neither be signalled nor clear a stale flag, so the gate would deadlock or be skipped. zdev also touches the old `/.zdev-sync-ready` as root, best effort, for template entrypoints documented to wait on it themselves; nothing in zdev reads it. Don't add your own `while [ ! -f ... ]` workaround - it's already there. Two invariants it depends on: the wrapper CLEARS the flag before waiting (it lives in the writable layer, so a container let through once would skip the gate on every later `docker start` and could never recover without `docker rm`), and `signalSyncReady` only touches the flag once every mount of that service flushed AND reported `Beta.Connected`. Opening the gate on a failed sync is what turned a sync problem into a dead container: the beta endpoint IS the container, so a service that exits on an empty directory takes down the session that would have filled it. A held gate is the safe state - the container stays alive and a later `zdev start` fixes it.
- **Every container-creation path must run `prepareMutagen()` first and pass the resulting `MutagenMounts` into `startServiceWithMutagen` / `buildContainerConfig`.** Look mounts up by `(service, container path)` via `Lookup`, never by service alone - a service can have several. Building a container with `mutagenEnabled=false` while the project actually has Mutagen mounts swaps the named `sync.<svc>.<project>.zdev` volume for a raw bind mount - dropping anything in the Mutagen ignore list (`vendor/`, `.setup-complete`) that lived only inside the volume. Has burned `zdev update` twice; covered by `TestProject_MutagenUpdatePreservesSyncVolume`.
- **Per-service Mutagen ownership (`services.<name>.mutagen.user/group/file_mode/directory_mode`)** maps to Mutagen's `--default-*-beta` flags and addresses the "files synced as root, but apache runs as www-data and can't read them" class of bugs. Drift is tracked via a hash file at `~/.zdev/mutagen/sessions/<session-name>`; on change `startMutagenSessions` terminates+recreates the session, and `applyPostSyncOwnership` runs `chown -R` inside the container so PRE-EXISTING files also pick up the new owner (Mutagen's flags only stamp NEW files). Don't drop the chown step thinking the flags handle it - they don't.
- **`zdev cleanup` reclaims networks too, and they are the scarce resource** (Docker's default pool is exhausted after ~31). A network is kept while ANY container references it - `docker ps -a --filter network=`, not the network's endpoint list, which shows only running ones. One project whose config fails to parse is skipped with a warning rather than aborting the run, and everything bearing its name is preserved; never make an unreadable config prune resources.
- **A container pins its network by ID.** If the project network is removed and recreated (another project's `zdev down`, a prune, a cleanup) while a container merely exists, Docker refuses to start it with `network <id> not found` - naming an ID, not the name, which is why it reads as unrelated. `startServiceWithMutagen` detects this via `isStaleNetworkError` and recreates the container; `RestartService` has no create path, so it points at `zdev start` instead.
- **Single-file bind mounts are inode-resolved, so they break when the file is REPLACED** (editors and anything that renames a temp file into place). The container keeps the deleted inode while the host file looks fine. Only `/proc/self/mountinfo` shows it, as a `//deleted` suffix on the mount root - `StaleFileMounts` reads that and `zdev status` reports it. Nothing can repair it in place; the container has to be restarted.
- **`zdev rename` migrates volumes via a temp container** using a project service image (guaranteed present locally). Docker has no native volume rename. See `CopyVolume` on the Runtime interface. Old volumes are removed LAST, only after state and config both carry the new name; any earlier failure rolls back the copies (a retry would otherwise be refused, since rename won't copy into an existing target volume).
- **The docs page (`docs.shared.<domain>`) is also Traefik's 404 catch-all** - unmatched URLs land there, not a generic error page.
- **Integration tests that tear down shared services** (router, mail, db, redis, logs) must snapshot beforehand and restore afterward via `snapshotSharedServices` / `restoreSharedServices`. Forgetting this silently breaks the developer's running environment.
- **New config fields break released binaries.** Config parsing uses `KnownFields(true)`, so a `.zdev/config.yaml` using an unreleased field fails to load on every installed zdev. Never adopt an unreleased config feature in a real project's config - it bricks the team's environment until the release ships.

## Docs to Keep in Sync

**Every user-visible change needs a docs check in two places: the human docs (`README.md` / `docs/`) AND the agent skill (`skills/zdev/`).** They cover the same features for different readers, so they are separate files, never symlinks (the skill is installed by copying `skills/zdev/` only, and agents need terse rules and gotchas, not explanations). Before calling a change done, check both and update whichever is affected, or say explicitly that neither needed changes.

- **`README.md`** - the lean entry page: intro, architecture, quick start, how it works / security, links. **Don't grow it**: new material goes into the matching `docs/<topic>.md` (or a new topic file linked from the README's Documentation line).
- **`docs/*.md`** - the human docs, one topic per file (`agents`, `cli`, `configuration`, `examples`, `project-commands`, `project-commands-justfile` (the deprecated justfile way, removed with just), `templates` (template authoring), `shared-services`, `https-and-dns`, `routing`, `file-sync`, `secrets`, `linking`, `installation`, `troubleshooting`, `credits`). Update the topic a change touches: new commands and flags in `cli.md`, config fields in `configuration.md`, and so on.
- **`skills/zdev/`** - the agent-facing skill (distributed via `npx skills add 0ploy/zdev`). **SKILL.md is a lean router** (~110 lines: ground rules with their reasons, core CLI, *using* `zdev run`, top problems, a task -> reference table); everything else lives in one `references/*.md` per task (`configuration`, `config-examples`, `existing-project`, `project-commands` (writing job files, converting justfiles), `debugging`, `secrets`, `linking`, `templates`, `stack-gotchas`). Put new material in the matching reference, not in SKILL.md, and add a row to the table for a new reference.
- **`CONTRIBUTING.md`** - developer onboarding (structure, testing strategy, how to add commands/services). Update it when architectural decisions or test patterns change.
- **`docs/architecture.html`** - source of the README's `architecture.png`. When a headline feature changes the picture, edit the HTML, screenshot it in Chrome at 1200px viewport width (2x renders 2400px), and compress to `docs/architecture.png` with `pngquant --quality=70-95`.
- **`Completo-Briefing.md`** - context for Completo's AI features. Regenerate with `/completo-briefing`.
- **`ALTERNATIVE_BACKENDS.md`** - Docker engine compatibility (Docker Desktop / OrbStack / Colima) and the cross-engine filesystem benchmark. Point-in-time analysis; refresh the numbers with `scripts/fsbench.sh` if engine behavior changes materially.
